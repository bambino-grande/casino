# Kazik

Казино на внутриигровой валюте **наеБАЛЛЫ**: за джекпот в слотах игрок получает картинку-приз.
Пополнение кошелька идёт картой через API Z-банка (учебный банк, `https://karim.top/zbank`). Донаты автору проекта идут рублями по СБП, мимо кошелька.
Оба платежа работают через один общий интерфейс оплаты.

Лабораторная работа №1, серверная часть: модульный монолит на Kotlin + Spring Boot.
Проверяется через Swagger.

## Что умеет

| Возможность | Как работает |
|---|---|
| Регистрация и вход | `POST /auth/register` создаёт пользователя в Keycloak, вход — кнопкой **Authorize** в Swagger (OAuth2 + PKCE) |
| Кошелёк наеБАЛЛОВ | баланс, история операций; под капотом журнал двойной записи |
| Пополнение | оплата учебной картой Z-банка прямо в запросе → `SUCCEEDED` → наеБАЛЛЫ на кошельке по курсу 1 к 1 |
| Слоты | автомат «Капибара Классик»: 3 барабана, таблица выплат, прогрессивный джекпот; три 🦫 — джекпот и анимация `CAPYBARA_RAIN` |
| Призы | три капибары — джекпот и случайная картинка из папки-тома `server/prizes`; коллекция игрока и сама картинка видны только владельцу |
| Донат автору проекта | рубли по СБП: реквизиты и код-комментарий; донат засчитывается сразу и попадает на стену донатеров |

Вывода наеБАЛЛОВ обратно в рубли нет: это внутриигровая валюта.

## Запуск

Нужны Docker и Docker Compose. Всё, что относится к серверу, лежит в `server/`, поэтому команды выполняются там:

```bash
cd server
cp .env.example .env
docker compose up --build
```

| Что | Адрес |
|---|---|
| Swagger | http://localhost:8081/swagger-ui.html |
| Keycloak (админка) | http://localhost:8080 — логин и пароль из `KEYCLOAK_ADMIN*` в `.env` |
| PostgreSQL | `localhost:5544` (порт меняется через `KAZIK_DB_PORT`) |

В realm `kazik` две роли: `USER` (играет, пополняет, донатит) и `ADMIN` (смотрит любые раунды, призы и платежи).
Демо-пользователи: `player` (USER) и `admin` (ADMIN), пароль — `KAZIK_DEMO_PASSWORD` из `.env`. Зарегистрированный через API получает USER.

### Сценарий проверки в Swagger

1. `POST /api/v1/auth/register` — зарегистрироваться (или взять `player`).
2. **Authorize** → `kazik-swagger` → войти на странице Keycloak.
3. `POST /api/v1/payments/top-ups` с заголовком `Idempotency-Key`, суммой и картой Z-банка
   (`number`, `expiryMonth`, `expiryYear`, `cvv`) → ответ `SUCCEEDED` или `422` с причиной отказа.
   Карту игрок заводит сам в Z-банке (`POST /api/auth/register`, `POST /api/auth/login`, `POST /api/cards`),
   а деньги на её счёт кладёт владелец банка: самостоятельного пополнения у Z-банка нет.
4. Через секунду `GET /api/v1/wallet` покажет наеБАЛЛЫ.
5. `POST /api/v1/games/slots/capy-classic/spins` — крутить. Повтор с тем же ключом не списывает ставку второй раз.
6. Джекпот выпадает редко (около раза в 13 800 спинов; в тестах случайность подменяется). Когда выпал, в ответе спина есть `prize`,
   а `GET /api/v1/rewards/prizes` показывает коллекцию, `GET /api/v1/rewards/prizes/{id}/image` отдаёт саму картинку.
7. `POST /api/v1/donations` — донат автору проекта (нужен вход): в ответе `SUCCEEDED`, реквизиты СБП (`sbpTransfer`) и код-комментарий;
   донат сразу виден на стене `GET /api/v1/donations` (стена открыта без входа).

### Картинки-призы

Картинки лежат файлами в папке `server/prizes` (в Docker это смонтированный том, `/data/prizes`). Сервер выдаёт случайный файл
(`png`, `jpg`, `webp`, `gif`, `svg`) и хранит в БД только его имя. Файлы можно добавлять без перезапуска.
Сейчас там два нейтральных образца `sample-1.svg` и `sample-2.svg`: замените их своими. Картинка отдаётся с заголовком
`Content-Security-Policy: sandbox`, поэтому скрипт внутри SVG не выполнится. Свои картинки git не отслеживает
(`server/prizes/*` в `.gitignore`, в репозитории только образцы). Если папка пуста, джекпот всё равно выплачивается деньгами,
а приз не выдаётся и в логе появляется ошибка.

## Тесты

```bash
cd server
./gradlew integrationTest  # интеграционные на PostgreSQL 18 в Testcontainers (нужен Docker)
```

Что проверено:
- **Гонки:** 50 параллельных ставок при балансе на 10 — проходит ровно 10, баланс не уходит в минус.
- **Идемпотентность:** повтор спина и пополнения с тем же ключом ничего не списывает повторно; тот же ключ с другими параметрами — 409.
- **Z-банк:** оплата картой синхронная; отказ банка — 422 с кодом (`CARD_INSUFFICIENT_FUNDS`, `INVALID_CARD_DETAILS`, `CARD_UNAVAILABLE`);
  успех на чужой счёт или с другой суммой не принимается; карта и CVV не попадают ни в БД, ни в логи.
- **Сбои:** таймаут или 5xx Z-банка — 503, платёж не считается отказом; повтор тем же ключом и картой уходит в банк с тем же ключом и завершает платёж без второго списания.
- **Деньги:** журнал сходится в 0, ставка и выигрыш идут через кассу `HOUSE`; донат по СБП не трогает кошелёк.
- **Проверки:** баланс проводки, ставка, суммы и маршрут оплаты проверяются в коде до записи в БД; в БД остаются ключи, уникальные ограничения (идемпотентность, один раунд — один приз) и индексы.
- **Схема:** пять миграций по модулям (`001-wallet` … `004-rewards`, `005-data` — начальное заполнение) применяются при старте, у каждого FK есть индекс.
- **Ошибки:** тест сканирует все исключения проекта и проверяет, что каждое ловит обработчик; каждый код ответа (400, 403, 404, 405, 409, 422, 503) проверен запросом.
- **Слоты:** RTP считается точным перебором всех 6³ комбинаций — 93% база + 2% в джекпот.
- **Призы:** джекпот выдаёт ровно один приз за раунд (повтор спина возвращает тот же), выдаются только картинки из тома, чужой приз и чужую картинку получить нельзя.
- **Хранение:** репозитории — обычные классы на `JdbcClient` с SQL, без JPA и Jakarta; значения всех колонок задаёт приложение.

            ├── payments/                         единый интерфейс оплаты, Z-банк, СБП, донаты
            ├── games/                            слоты, раунды, пул джекпота
            └── rewards/                          призы за джекпот: каталог картинок в томе, коллекция игрока

Доменные модули (`wallet`, `payments`, `games`, `rewards`, `identity`) лежат внутри одного Gradle-модуля обычными пакетами.
Общаются они через пакет `api` (`wallet.api`, `payments.api`, `rewards.api` — типы и события) и интерфейсы сервисов в `business.services`.

Внутри каждого доменного модуля слои `business` (домен, сервисы, порты), `infrastructure` (репозитории на `JdbcClient`, HTTP-клиенты, планировщики),
`presentation` (контроллеры, DTO, мапперы) и `security`.

### Модули почти не общаются

```
 games   ──transfer─────────────▶ wallet ◀──событие PaymentSucceeded (outbox → inbox)── payments
 games   ──приз за джекпот──────▶ rewards
 identity: ни с кем — JWT проверяется в каждом модуле локально
```

- **Связь двумя способами:** синхронный вызов через интерфейс (`games` → `TransferService` кошелька и `PrizeService` призов) или событие через Transactional Outbox / Inbox. Сейчас это один процесс и одна БД, поэтому спин выполняется в одной транзакции.
- **Данные раздельно:** у каждого модуля свои таблицы (`wallet` — счета и журнал, `games` — раунды и пул, `payments` — платежи и outbox, `rewards` — призы), внешних ключей между таблицами разных модулей нет.
- **Сейчас всё в одном процессе:** модули вызывают друг друга обычными вызовами Kotlin, событие доставляется внутри процесса; ни Kafka, ни HTTP между модулями нет. HTTP — только к внешним Z-банку и Keycloak.
- **Распил на микросервисы (если понадобится):** заменить вызовы кошелька и призов на HTTP-клиент (адаптеры `WalletTransferGateway` и `PrizeServiceGateway` в `games`), `InProcessIntegrationEventBus` — на Kafka или RabbitMQ, вынести пакет нужного модуля в отдельный Gradle-проект и дать ему свой запускаемый класс. Бизнес-код не меняется.

### Деньги и конкурентность

- **Двойная запись:** каждая операция — проводка с суммой 0. Системные счета: `HOUSE` (касса казино) и `GATEWAY` (деньги от провайдера).
- **Изоляция READ COMMITTED.** Гонки закрыты явно, без SERIALIZABLE:
  - атомарный `UPDATE ... WHERE balance + delta >= 0`;
  - блокировка счетов в порядке id, поэтому нет deadlock;
  - уникальный `reference` пишется первым и сериализует повторы;
  - пул джекпота берётся `SELECT ... FOR UPDATE`;
  - поле `version` у платежа — оптимистическая блокировка (`UPDATE ... WHERE version = ?`).
- **Спин:** одна транзакция (`@Transactional` на `SpinService.spin`): списание ставки → барабаны и джекпот → зачисление выигрыша → запись раунда.
  Любой сбой откатывает всё целиком, поэтому «зависших» раундов и фоновой сверки нет. Повтор с тем же `Idempotency-Key` возвращает прежний результат,
  а параллельный повтор получает 409 `ROUND_IN_PROGRESS`.
- **Где `TransactionOperations`:** только в платежах и outbox — там внешний вызов (Z-банк) должен идти вне транзакции. Остальное — `@Transactional`.

### Платежи

`PaymentProvider` — единый интерфейс: `method` и `create`. Статусы платежа: `CREATED`, `SUCCEEDED`, `FAILED`, `EXPIRED`.

| Провайдер | Для чего | Как подтверждается |
|---|---|---|
| `ZBankPaymentProvider` | пополнение наеБАЛЛОВ | сразу в ответе: банк списывает с карты синхронно |
| `SbpTransferPaymentProvider` | донат автору проекта | засчитывается сразу: реквизиты и код `KZK-XXXXXX`, сам перевод сервер не проверяет |

Донат по СБП не проверяется: у перевода на личный номер нет API и уведомлений, поэтому сервер не знает, пришли ли деньги,
и на стене может оказаться донат без перевода. Настоящее подтверждение даст СБП через эквайринг: это отдельный адаптер `PaymentProvider`.

Какой метод разрешён для какой цели, решает `PaymentRoutingPolicy`.
Вызов провайдера идёт вне транзакции, с `operationId` как ключом идемпотентности.
Если ответ Z-банка потерялся, платёж остаётся `CREATED`, и плательщик завершает его повтором с тем же `Idempotency-Key` и той же картой
(CVV мы не храним, поэтому сервер сам повторить не может). Неоплаченный платёж через 30 минут становится `EXPIRED` (фоновая задача раз в минуту),
но тот же повтор всё ещё может его завершить: Z-банк по тому же ключу второй раз не спишет.
Ключ, счёт Z-банка и телефон СБП проверяются при старте: без них приложение не запустится.

**Контракт Z-банка** — по документации владельца (`API_INTEGRATION.md`, версия 1.0 от 22.10.2026), только партнёрские методы:

```
POST /api/partner/payments       Authorization: Bearer <ключ магазина>, Idempotency-Key: kazik-topup:<operationId>
     {"number":"4000000000000002","expiryMonth":10,"expiryYear":2029,"cvv":"007","amountKopecks":50000}
  → 200 {"id":"…","kind":"PAYMENT","status":"SUCCEEDED","amountKopecks":50000,"destinationAccountId":"<счёт магазина>",…}
  → 422 {"id":"…","kind":"PAYMENT","status":"DECLINED","errorCode":"INSUFFICIENT_FUNDS",…}   сохранённый отказ
  → 409 {"code":"CONFLICT",…}   тот же ключ с другой картой или суммой
```

Успехом считается только `kind=PAYMENT`, `status=SUCCEEDED`, `errorCode=null`, наша сумма и наш счёт (`ZBANK_ACCOUNT_ID`).
Вебхуков, страницы оплаты и возвратов у Z-банка нет. Ключ и счёт магазина задаются в `.env` (`ZBANK_API_KEY`, `ZBANK_ACCOUNT_ID`) и в репозиторий не попадают.

### HTTP-ошибки

Тело ошибки: `{code, message, status, timestamp, traceId}`. Заголовок `traceId` есть в каждом ответе и в каждой строке лога.

| Статус | Когда |
|---|---|
| 400 | валидация |
| 401 | нет токена |
| 403 | нет прав |
| 404 | не найдено |
| 405 | метод не поддерживается |
| 409 | ключ идемпотентности, параллельный повтор, конфликт версий |
| 422 | не хватает наеБАЛЛОВ, банк отказал в оплате, бизнес-правило |
| 503 | Z-банк или Keycloak недоступны — операцию можно повторить |
